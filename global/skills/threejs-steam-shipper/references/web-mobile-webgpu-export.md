# Web, Mobile, And WebGPU Export Notes

Research baseline: checked against current Three.js, MDN WebGPU, and Apache Cordova documentation on 2026-08-08.

## Shared Static Build

Use one production static web build as the input for desktop, web, and mobile targets. For Vite, keep `base: './'` unless the hosting path is known. Verify that runtime asset URLs, workers, WASM decoders, fonts, locale JSON, and audio files resolve from a nested folder and from Cordova `www/`.

Do not require a live backend for a packaged game unless the original game already needs one. If the game has online services, keep offline failure states explicit.

## Static Web Export

Create `buildable/web/dist/` as the uploadable artifact. Include a short checklist for:

- serving over HTTP/HTTPS, not `file://`, for browser QA;
- fullscreen and pointer-lock flows;
- touch and keyboard input;
- audio unlock after user gesture;
- local storage or IndexedDB saves;
- cache headers/service worker behavior if the project already uses them;
- WebGPU secure-context behavior and WebGL fallback.

## Cordova Mobile Export

Use Cordova as a native WebView wrapper around the same static web build:

```text
buildable/mobile-cordova/
  package.json
  config.xml
  www/
  scripts/copy-web.mjs
```

Keep native platform folders generated by Cordova, not handwritten. The agent may create `config.xml`, `package.json`, copy scripts, and checklists, but it should tell the user/agent to install platform requirements before building:

- Node/npm and Cordova CLI.
- Android Studio, Android SDK, JDK/Gradle requirements for Android.
- macOS with Xcode, command line tools, CocoaPods, and signing/provisioning for iOS.

Prefer minimal plugins. Add orientation/fullscreen/status-bar plugins only when the game's UX requires them. Do not add camera, file, ads, billing, analytics, or push plugins unless the game already needs those capabilities.

Mobile QA must include:

- touch controls and pointer events;
- orientation lock or responsive layout;
- notch/safe-area handling;
- pause/resume/background audio behavior;
- context loss and low-memory recovery;
- texture size and GPU memory limits;
- first launch without network;
- Android APK/AAB or iOS archive signing only after debug builds run.

## WebGPU Progressive Port

Three.js `WebGPURenderer` can target WebGPU when available and fall back to WebGL 2 for supported features. Use that path only when the installed Three.js version supports the imports used by the project.

Recommended approach:

- Add a small renderer factory such as `src/rendering/createThreeRenderer.mjs`.
- Prefer `import { WebGPURenderer } from 'three/webgpu'` for the progressive path and keep `WebGLRenderer` as the conservative fallback.
- Feature-detect `navigator.gpu` and expose a force-WebGL option such as `?renderer=webgl` for QA.
- Avoid WebGPU-only compute or unsupported node/material features unless the game can ship without WebGL fallback.
- Verify WebGPU in a supported secure context and verify WebGL fallback on unsupported browsers, mobile WebViews, and Electron if WebGPU flags/runtime behavior vary.

If WebGPU support is uncertain, ship WebGL first and leave the adapter scaffold with a report explaining what must be ported.
